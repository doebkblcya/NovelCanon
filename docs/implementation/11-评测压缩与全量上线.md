# 11 评测、压缩与全量上线

## 目标

通过短篇和长篇 Pilot 冻结质量与成本基线，决定是否启用压缩，随后完成全量建库、备份恢复、API 和持续回归。

## 前置条件

- 阶段 01–10 已形成完整、可计量的管线。
- 原文不压缩基线能够稳定运行。
- 验收阈值在查看正式评测结果前写入测试配置。

## P1：短篇整本 Pilot

使用约 30 万字完整小说，对比：

1. 原文 hybrid 基线；
2. 原文结构化管线；
3. 可选压缩结构化管线。

评测至少包含：

- 核心/全部实体合并 F1；
- 事实 precision/recall；
- direct evidence hash 复现率；
- QA 引用章节正确率；
- 因果边 precision；
- 重试和原子激活；
- 每万字 Token、时间和成本。

阈值以《定版方案》§14.2 为准。

## 压缩实验

### 1. 规则预扫描

扫描专名、数字、时间、高频意象和重复短语，生成逐字保留词典，不调用生成模型。

### 2. 受约束改写

每段输出 keep、rewrite、drop、reason 和稳定 ref_seg。题材及输出保留率记录在 compression version 中。

### 3. 后验校验

比较实体、数字、时间表达和豁免词覆盖率；低于阈值的段自动回退原文。

### 4. 决策门

只有压缩管线事实 recall 相对原文线下降不超过 0.02，证据复现和关键 QA 不退化，且成本收益足够明确时，才允许默认启用。不同题材可采用不同策略。

## P2：长篇质量 Pilot

使用连续 200–300 章主样本，并增加开头、中段和结尾窗口。重点验证：

- 跨百章实体合并；
- 后期身份揭示；
- 长程状态和关系演变；
- 因果链断裂率；
- cutoff 与 world time 独立安全性；
- 卷/全书摘要覆盖率；
- 数据库、索引和队列的线性扩展性。

## P3：全量建库

全量前完成：

- 容量与 Token 预测；
- 数据库和原始输入备份；
- checkpoint 恢复演练；
- 索引重建演练；
- 磁盘空间和 WAL 监控；
- 限流及日预算；
- 失败章节人工处理流程。

全量运行采用逐阶段闸门，不应在 Map 未验收时继续执行 canonical/link/reduce。

## P4：查询 API

- API 调用复用 CLI 的 application service。
- 请求必须包含明确 book_id。
- 支持 knowledge cutoff 和 world at chapter。
- 返回事实、证据、章节和运行版本。
- 增加超时、分页、限流、审计日志和稳定错误码。
- 不在 API 层复制时间过滤业务逻辑。

## P5：持续评测

- 冻结黄金集并纳入 CI/定期任务。
- Prompt、profile、ontology、Schema、索引或查询改动均触发对应回归。
- 分别观察质量、延迟、吞吐和 Token。
- 新增事实类型或查询路线前先修改定版方案。
- 定期执行数据库完整性、证据复现和 cutoff 泄露扫描。

## 产物

- P1/P2 评测报告；
- 三路线质量与成本对比；
- 压缩启用/禁用决策记录；
- 全量运行手册；
- 备份、恢复和重建工具；
- 查询 API；
- 持续回归集和监控指标。

## 验证

- P1/P2 达到冻结阈值。
- 全量任务可以从模拟故障中恢复。
- 数据库恢复后通过 foreign key 和证据完整性检查。
- API 与 CLI 对相同查询返回一致事实集。
- cutoff 泄露回归为零。
- Token 账本覆盖全部模型调用。

## 最终退出标准

- 目标长篇完成单一 active 全量 run。
- 所有正式回答可追溯到 supported evidence。
- 备份、恢复、索引重建和失败重跑均经过演练。
- 质量、成本、吞吐和错误率有持续可观察基线。
- 后续变更遵循“先契约、再 migration、再代码、最后重建/回归”的流程。

## 实现记录（阶段 11 交付）

### 模块

- 评测：`eval/`（golden.py 黄金集 / metrics.py 指标计算 / pilot.py 三路线
  Pilot）——QA 引用章节正确率、事实 precision/recall、实体合并 F1、
  证据 hash 复现率、因果边 precision；Pilot 报告 JSON 可序列化；
  fixture 黄金集由 GOLDEN_CHAPTERS（4 章黄金样例）构造并冻结。
- 压缩：`compression/`（prescan 规则预扫描→rewriter 受约束改写
  keep/rewrite/drop/reason/ref_seg→PostValidator 后验校验自动回退→
  DecisionGate 决策门）——决策门四条件（recall 差 ≤0.02 / 证据复现不
  退化 / QA 不退化 / 成本节省 ≥10%）才允许默认启用压缩。
- 备份恢复：`storage/backup.py`——SQLite 在线备份（WAL 安全）+ 恢复 +
  verify_integrity（FK / 证据 span hash 复现 / claims 幂等）。
- 持续回归：`ops/scan.py`——scan_cutoff_leakage（来源章节 ≤ cutoff，
  泄露回归为零）+ scan_integrity；CI 增加黄金集回归 + 完整性扫描步骤。
- 查询 API：`api.py`（FastAPI）——复用 QueryExecutor（不在 API 层复制
  时间过滤逻辑），book_id 必填、cutoff/world_at、分页、进程内限流、
  审计日志、稳定错误码（missing_book/book_not_found/rate_limited/
  invalid_params/internal）、/explain 路由诊断。
- CLI：pilot / compress / backup / restore / scan-leakage / serve。
- 全量运行手册：docs/implementation/11-全量运行手册.md（容量预测、备份
  恢复演练、逐阶段闸门、监控、失败处理、索引重建、最终验收）。

### 关键决策

1. 黄金事实描述与 _predict_facts 提取格式对齐（canonical id 而非表面名），
   保证事实 precision/recall 可比。
2. 压缩确定性路径（无模型）可测；LLM 改写器接口预留（keep/rewrite/drop/
   reason/ref_seg 结构化输出）。
3. 后验校验的段索引与 Compressor 段列表一致（过滤空段后对齐），避免
   索引错位导致全量误回退。
4. Pilot 三路线：structured（QueryExecutor）/ hybrid（RetrievalService
   章节定位）/ compressed（决策门通过后接入）。

### 验证对照

- 指标计算器单元测试 + Pilot 黄金 4 章端到端（事实 recall>0、cutoff
  过滤后 recall 下降）；
- 压缩保留词典/逐段决策/后验回退/决策门四条件；
- 备份→删库→恢复→FK 与证据完整性通过；外键破坏可检出；
- API 与 QueryExecutor 同查询一致事实集（章节集合相同）、限流/错误码/
  cutoff/world_at/分页；
- cutoff 泄露扫描真实库 9 检查零泄露。

### 验收修复记录（阶段 11 复审五轮：P0×2 + P1×1 闭环）

1. **[P0] 正常 /query 请求错误超时（30s 后 408）**：上一轮同步端点 async
   化已绕开 anyio，但 ThreadPoolExecutor + `asyncio.wrap_future` 的完成
   通知在锁定环境仍不可靠——正常查询提交到线程池后 30 秒未完成、触发
   408。根治：**移除线程池，同步 executor（默认 QueryExecutor）在事件
   循环内直接执行**——不提交线程、不依赖任何线程调度/完成通知，正常
   查询必定及时完成；代价是请求期间占用事件循环（低并发 API 可接受，
   uvicorn 多 worker 横向扩展）。超时保护（408）保留给**异步 executor**
   （executor_factory 注入，`inspect.iscoroutinefunction` 检测后经
   `asyncio.wait_for` 可取消）。新增回归测试
   `test_query_normal_query_does_not_timeout`（request_timeout=1s 下正常
   查询必须 200）；`test_query_timeout` 改用异步 SlowExecutor 验证 408。
2. **[P0] 压缩路线与基线路线证据分母不一致**：基线用
   `golden.evidence_spans`（GoldenSet 独立冻结字段），压缩路线误用
   `golden.claims[*].evidence_span`——人工冻结的额外证据只出现在
   evidence_spans 时会被漏掉，缩小分母、虚高复现率、可能错误放行决策
   门。统一：压缩路线（run_compressed_route 与 _reingest_compressed_book）
   的证据复现分母一律用 **golden.evidence_spans 去重**（与基线同一

### 验收修复记录（阶段 11 复审八轮：P1×1 闭环）

1. **[P1] 线程池 worker 非 daemon，卡死任务阻止进程退出**：实测 CPython
   3.13/3.14 的 ThreadPoolExecutor worker 为**非 daemon**（此前注释误判为
   daemon），且 `concurrent.futures.thread` 注册 atexit `_python_exit`——
   解释器退出时显式 join 所有 worker（与 daemon 无关），运行中的卡死任务
   会**阻止进程关闭**（子进程实测：`shutdown(wait=False)` 后 sleep 任务仍
   把解释器退出拖死 >30s）。修复：
   - 弃用 ThreadPoolExecutor，改用**自管 daemon 工作线程池**
     `_DaemonQueryPool`（threading.Thread(daemon=True) + queue.Queue，
     **不注册 concurrent.futures 的 atexit join**）：解释器退出时 daemon
     线程被直接终止，卡死任务永不阻塞进程退出；对外仍返回
     `concurrent.futures.Future`（done()/result()/add_done_callback/cancel
     语义不变，轮询与 done callback 逻辑不改）；
   - **严格下游超时**：`OpenAICompatEmbedder` 超时参数化
     （timeout_seconds，默认 30s）——运行中任务无法强制中断，靠下游有限
     超时保证线程最终自然结束、资源回收；
   - lifespan 关闭语义保持：cancel_futures 取消排队任务，运行中任务继续
     （daemon 不阻塞关闭）。
   回归测试：`test_process_exits_with_stuck_pool_task`——**子进程**中启动
   永不结束的卡死任务 → lifespan 关闭 → 进程在限定时间内正常退出
   （非 daemon/atexit-join 行为会在子进程 timeout 处被杀）。

### 验收修复记录（阶段 11 复审九轮：P1×1 闭环）

1. **[P1] submit() 与 shutdown() 关闭竞态可产生永不完成的 Future**：
   `submit` 对 `_shutdown` 的检查与 `queue.put` 之间无同步——若 shutdown
   恰好在此窗口执行，会先清空队列并放入退出哨兵，任务随后排在哨兵
   之后，worker 全部退出后任务永不执行也永不取消（Future 悬挂）。修复：
   - `_DaemonQueryPool` 增加 `threading.Lock`：**同一把锁**保护 submit
     （检查 _shutdown + 创建 Future + 入队）与 shutdown（置 _shutdown +
     清队列取消 + 哨兵入队）——关闭后 submit 抛 RuntimeError，杜绝
     「任务排在哨兵之后」；
   - 回归测试 `test_pool_submit_shutdown_race_no_hanging_futures`：50 轮
     × 4 线程高并发 submit/shutdown 交错——所有被接受的 Future 必须
     done（执行或取消）。已用**无锁版本注入验证**测试确实捕获竞态
     （round=0 即复现 4 个悬挂 Future）；加锁后 50 轮零悬挂。
     注意：被 shutdown 取消的 Future 状态为 CANCELLED（f.done()=True），
     concurrent.futures.wait 只把 CANCELLED_AND_NOTIFIED/FINISHED 计入
     done——判定用 f.done() 逐个检查（与 ThreadPoolExecutor 语义一致）。
